## One observed source defect: weak re-read of full HF base

**Stable error_id proposal:** `NOX-P0-HYBRID-V135-UNPINNED-HF-BYTES-AND-MODE-20261115`.

In V135 `verify_inputs(student, data, output, native)`, the currently visible safety check enumerates local `*.safetensors` and verifies only `sum(p.stat().st_size) == native["student_shard_bytes"]`, while accepting a syntactically valid `native["student_base_sha256"]`. This function **does not hash the shard contents at point of use**, nor hash the actual tokenizer/config files, and has no explicit training-mode lineage. The signed native admission can attest a prior snapshot but cannot by itself prevent local files changing between attestation and training. An unrelated same-size tensor change passes this particular check.

**Reproduction (local source-equivalent, not a native V135 run):** create `model.safetensors=AAA`, record size 3; overwrite with `BBB` size 3; old size-only condition returns `True` while bytes differ. The current full-optimizer checkpoint gate tests file tree SHA but does not address re-read of the input base. Combining PEFT into that runner without mode separation adds a resume hazard: a LoRA optimizer must never be treated as the full ZeRO-3 optimizer. This second issue is a **prevention requirement**, not a demonstrated existing cross-mode resume bug.

1. Add a **signed `NOX_HYBRID_HF_LINEAGE_V1`** manifest, based on an owner-readback of the actual existing trainable HF base: immutable HF repository identifier + commit revision (40 hex for git SHA; SHA256 where applicable), licence, architecture/config identity, tokenizer files and chat-template SHA, each safetensors file name/size/SHA256, total parameters, dataset/train+holdout hashes and current exact GPU1 source. The signed owner approval must bind this manifest and path. Require a verified owner-scoped manifest; do not substitute fake sha strings, names, timestamps or adapter metadata. Use manifest path allowlisting and deny symlinks/path escapes. Re-hash all original files in a bounded streaming read immediately before allocating the model and recheck lease/STOP after hashing. If a file changed, `HOLD_HF_FILE_SHA_MISMATCH`; a missing/unknown revision/licence/tokenizer is `HOLD_HF_IDENTITY_UNPROVEN`. Consider hardlink/inode checks or a read-only immutable snapshot to close post-hash TOCTOU; never declare cryptographic identity from a size tally.
2. Preserve the existing `FULL_ZERO3` entrypoint, `admit_resume`, optimizer state, `no_adapters`, original STOP/backup semantics **unchanged**. Add a separate explicit `training_mode` branch to this same FORGE lineage, not a second trainer/backend: `LORA_FP16`, `RSLORA_FP16`, optional `QLORA_NF4_FP16`. Verify installed PEFT/Transformers/bitsandbytes exact compatibility before loading (not blanket installing). Target module names must exist in the actual architecture; record trainable vs total parameters. Standard LoRA r=16 and 32 as bounded candidates, `use_rslora` only when selected, microbatch based on actual GPU1/CPU/disk reserves. On V100 `torch.float16` compute; no forced BF16, FP8, FlashAttention2/3 or non-SM70 kernels. Optional NF4 requires per-mode runtime test, rather than being assumed usable/faster.
3. **Resume metadata must be mode-locked**, not inferred from the presence of checkpoint files: `training_mode`, immutable base identity/revision/config/tokenizer hashes, PEFT type, adapter config hash, `r`/alpha/`use_rslora`, target modules, precision/quantization, dataset SHA, optimizer param group schema, exact `global_step` plus optimizer/scheduler/RNG readback and external restore. Mismatch -> `HOLD_RESUME_TRAINING_MODE` or `HOLD_RESUME_LINEAGE`. Full ZeRO-3 resume refuses adapter metadata; LoRA/QLoRA resume refuses arbitrary full optimizer state. Transition LoRA→full is a **new** optimizer/run with a new full-weight checkpoint, never the old LoRA optimizer resume. Treat an HF PEFT adapter-only checkpoint as **insufficient** evidence of optimizer/RNG durability until read back separately. Record actual optimizer steps from the authenticated trainer, not time or an adapter directory.
4. Adapter merge only into a fresh, isolated **unquantized copy of that exact base** after same-prompt independent holdout; compare base+adapter vs merged model using [1D independent evaluator](1D.md), and retain full lineage, adapter and original optimizer rollback. Never merge into the live GGUF or a repeatedly quantized base. Quantization and promotion require owner-controlled draining/readback on the original OneHost and a restored offsite checkpoint; original WEB/S03/weights retained.
