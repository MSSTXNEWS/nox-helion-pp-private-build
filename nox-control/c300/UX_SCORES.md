# UX_SCORES (UI): как считаются U и A

Замер: `bundles/ui_score/score.py` (запуск ui_sc1.sh, сводка report.py / ui_scr.sh). Страницы по `/web/<page>.html`, 1440x900 и 390x844 (mobile), результат = среднее по двум вьюпортам. Внешний критик и qa_audit не используются (медленные и нестабильные).

## Входные данные на страницу и вьюпорт
- Lighthouse (чистая headless Chrome, categories): a11y, best-practices (bp), performance (perf), 0-100.
- axe-core: нарушения с весом по важности (critical/serious = 2, moderate = 1, minor = 0.5), число узлов на правило ограничено 5; сумма = V.
- Свои метрики: T = число видимых кнопок/ссылок/полей меньше 44 px (без FullCalendar, Leaflet attribution, aria-hidden); H = горизонтальный скролл (0/1); C = есть видимый главный CTA (.u-cta, sl-button primary, .pri) (0/1); E = есть ошибки JS или больше 2 ответов 4xx (0/1); M = тема Графит активна (0/1).

## Формулы (0-10)
- u_own = 10 - min(4, 0.25*V) - min(2, 0.2*T) - 1.5*H - 1.0*(1-C) - 3*E  (не меньше 0)
- **U = 0.6*u_own + 0.4*(a11y/10)**  (если Lighthouse не отработал: U = u_own)
- a_own = 10 - 5*(1-M) - min(3, 0.3*T) - 2*H - 1.5*E  (не меньше 0)
- **A = 0.3*a_own + 0.4*(bp/10) + 0.3*(perf/10)**  (если Lighthouse не отработал: A = a_own)

Цель: U >= 8 и A >= 8 на каждой странице. Это прокси-метрики (доступность, технические дефекты, тема, CTA), а не оценка красоты: «эстетика» A выражается через best-practices, скорость и аккуратность (цели, скролл, тема). Perf на нагруженном сервере шумит, поэтому вес 0.3.
