# LESSONS — уроки на ошибках (читать перед каждым шагом)
Формат: что → почему → правило.

1. Чистка k_clean6 удалила /workspace/nox/ops/draw → чат упал на импорте → правило: удалять только по белому списку и после grep импортов/процессов по пути.
2. Команда владельца «добавь забытое, остальное раздели на V2/V3» понята с 4-го раза → координатор начал останавливать и переносить → правило: «добавь» ≠ «останови/перенеси/сузь»; текущая работа продолжается.
3. Каждый шаг отдельным запуском Actions (3–5 мин) → работа шла в разы медленнее → правило: 5–10 действий в одном скрипте, долгое — фоном, сборка и тест офлайн, на сервер — один раз пакетом.
4. Опрос gh run каждые секунды → общий лимит API 5000/ч исчерпан → правило: id из URL, опрос ≥45 с, p2_run.sh.
5. Повторный запуск со старым именем скрипта цеплялся к упавшему прогону → правило: новое имя скрипта на каждый запуск.
6. Оптимизация железа делалась только по напоминанию владельца → правило: фундамент первым (среда → готовое из интернета → оптимизация → функции), сам, без напоминаний.
7. add() в k8_s2 искал "nox-$2.js" и принял nox-live.js за nox-k8-live.js → K8live не подключён, QA упал, index откатился → правило: проверять подключение по точному имени файла (./nox-k8-X.js), не по подстроке.
8. QA index на 390 попал на редирект в chat (мобильная версия) → ложная ошибка и откат → правило: на мобильном открывать index?home=1.
9. /img/generate при обучении отвечает {"error":"korea_img_disabled"} (генерация только на GB10) → студия молча писала «картинка не получена» → правило: показывать пользователю error/reason ответа; /vision/describe отвечает {"text":...}.
10. /svc/advisors/* в браузере ведёт не на шлюз :8793 (v1/models 404) → старшие по рисованию из UI недоступны, пока V не даст маршрут → правило: перед встраиванием проверять маршрут из браузера, а не только localhost на сервере.
11. Параллельные запуски Actions подряд (recon3) → Vast API 429 «Too Many Requests», прогон упал → правило: не запускать несколько прогонов одновременно, при 429 подождать и повторить с новым именем (C).
12. Одиночные recon-прогоны по 3–5 мин → медленно → правило: recon, деплой и тест в одном скрипте, долгий тест фоном (nohup) и результат одним коротким прогоном (C).
13. (P3) renice -n -5 в контейнере не сработал (ni остался 0, нет CAP_SYS_NICE) → приоритет чату через nice недоступен → правило: чату — выделенные ядра (taskset), остальным nice +10..19; отрицательный nice не планировать.
14. (P3) %CPU в ps = среднее за всё время жизни (8106 «188%» при 0% сейчас; chrome 187 мин CPU) → ложные виновники → правило: пожирателей искать по top -H в окне 20–60 с, а не по ps pcpu.
15. (P3) Зависшие one.py/playwright (voice.html, 5+ ч, 7 процессов chrome по 70% CPU каждый) жили при nice 15 и ели ~5 ядер → QA без таймаута → правило: у каждого QA-запуска timeout (timeout 120 python one.py), охранник p3_cpuset_guard убирает процессы старше 2 ч.
