# ORCH_PLAN — итоговый план оркестрации субисполнителей NOX HELION

Сводка консилиума (эксперты: железо, архитектура, UX). Пожелания владельца сохранены по смыслу; реализация — минимум LLM-звеньев, максимум готового кода.

## 1) Схема в 12 строк

```
 1. Владелец → короткая команда в чат (слот 0, всегда свободен, n-gram spec-decoding)
 2. Intent-классификатор (словарь намерений + embeddings) → fast path (60–70%) сразу исполнителю
 3. «Смекалка+Архитектор» = Planner: 1 вызов основной модели → plan.json (цель, done-if, подзадачи, verify, роли, N, класс проверяемости)
 4. Советник качества/скорости = 2-й вызов (Critic) только для сложных задач: правит plan.json волной
 5. NOX формулирует цель владельцу одной строкой (из plan.json, без нового вызова)
 6. Диспетчер-код: SQLite-очередь, lease-лидер, ≤3 слота задачам, модель/LoRA/внешний по роли
 7. Страж (2-й диспетчер): systemd-таймер + lease-строка; перехват лидерства, перезапуск зависших
 8. Исполнители (до 10 очередей, ~4 одновременных декода): git worktree, срез blackboard, бюджет
 9. Тренер: правила по триггерам (таймаут, повтор ошибки, токены) → редкий LLM «смени подход»
10. Ревизор: детерминированные verify → судья другой модели по рубрике → адресный возврат
11. NOX смотрит итог, показывает карточку «Принять / Доработать / Откатить»
12. Арбитр GPU: чат > исполнители > обучение; события SSE → UI (статус → доска/граф → лог/артефакты)
```

## 2) Таблица звеньев

| Звено (пожелание владельца) | Реализация | Готовый open-source компонент |
|---|---|---|
| NOX — чат, цель, показ итога | основная модель (Qwen3.6-35B-A3B), слот 0 | llama.cpp server + llama-swap |
| 1–2 советника «на смекалку» (словарь намерений) | классификатор + Planner-вызов (слито) | semantic-router / SetFit на bge-m3; пороги уверенности |
| Переспросы | только если уверенность < порога и нет безопасного дефолта | — (правило в коде) |
| Советники качества/скорости + архитектор | 1 вызов Planner (JSON-схема) + опц. 1 вызов Critic | llama.cpp `--json-schema`/GBNF, Outlines-схемы |
| Диспетчер | код | SQLite + huey/`litequeue`, asyncio; httpx к /slots |
| Второй диспетчер (контроль) | код-страж, lease TTL | systemd timer/watchdog, supervisord |
| Перезапуск всех | код | systemd `Restart=`, llama-swap ttl/reload |
| Микро-ревизор (тренер) | правила + редкий LLM (нано-LoRA или основная) | собственные триггеры (~150 строк) + Langfuse-метрики |
| Исполнитель-кодер | спец-модель / основная | Qwen2.5/3-Coder GGUF, OpenHands / aider как обвязка |
| Исполнитель-UI-дизайнер | спец-модель + vision-проверка | UI-модели GGUF (UIGEN-класс), Playwright-скриншоты + vision |
| Прочие исполнители (текст, поиск, данные) | основная модель с ролевым промптом | smolagents / LangGraph-узлы, SearxNG |
| Ревизор | verify-команды → судья другой модели | pytest/ruff/eslint/Playwright; судья — уже имеющиеся judges |
| Внешние советники из интернета | внешний API в волне консилиума | OpenRouter/бесплатные tier'ы, через LiteLLM |
| Blackboard | файлы + git | task.md, plan.json, decisions.log, artifacts/, git worktree |
| Арбитр (обучение уступает) | код | systemd-слайсы + сигналы паузы; Unsloth/axolotl для обучения |
| Наблюдаемость/бюджет | код | Langfuse (self-host), llama.cpp `--metrics` + Prometheus |
| UI | фронт | xyflow (граф), SSE, готовый kanban-компонент |

Итог: до работы — 1–2 LLM-вызова вместо ~10. Всё «управленческое» — код.

## 3) Параметры сервинга

- Движок: llama.cpp + llama-swap (vLLM на Turing не оправдан).
- Основная: `-np 4 -c 131072` (~32k/слот), `-fa on`, `--cache-type-k q8_0 --cache-type-v q8_0`, `--cache-reuse 256`, `--slot-save-path`, `--metrics`, `--mlock`.
- Слот 0 — чат NOX, всегда; диспетчер занимает ≤3 слота. Spec-decoding n-gram только на чат-слоте.
- Одинаковый префикс промптов ролей (системная часть + схема) → кэш.
- Нехватка VRAM: `--n-cpu-moe N` (эксперты в RAM, 128 ГБ хватает).
- llama-swap: группа `persistent` для основной модели; ttl для coder/UI/судьи; не сажать задачу при свободной VRAM < 3 ГБ (проверка через nvidia-smi/NVML в диспетчере).
- LoRA: только на dense нано-базе 1.5–4B (роутер, тренер), не на MoE.
- Обучение: только в простое; на время обучения воркеры `-np 1`, чат-слот сохраняется; при сообщении владельца — пауза обучения (арбитр).
- Реальная пропускная способность: ~4 одновременных потока, 250–400 ток/с суммарно. «10 субисполнителей» = 10 очередей.
- Диск (~10 ГБ): не держать больше 1 спец-модели на диске сверх нужного; кэш слотов чистить по LRU.

## 4) Консилиум волнами

- Волна 1: Planner (основная модель) → plan.json.
- Волна 2: Critic видит plan.json и улучшает (качество/скорость, N, риски) — диф-правки, не переписывание.
- Волна 3 (только для задач класса «сложно/дорого ошибиться»): внешний советник из интернета видит обе версии, даёт правки.
- Волна 4: судья проверяет, что done-if исполнимы; NOX сводит и формулирует цель.
- Стоп-правило: следующая волна запускается, только если предыдущая изменила план существенно (diff > порога) или уверенность низкая. Простые задачи — 0 волн (fast path).
- Документы владельца (концепция и ТЗ) — приоритет над мнением консилиума; подаются в префикс Planner.

## 5) UX-слои

1. Строка-статус в чате: «4/7 готово · кодер правит API · ~3 мин»; чат не блокируется.
2. Доска: канбан (Очередь / В работе / Проверка / **Нужен ты** / Готово) + граф исполнителей (xyflow).
3. Лог и артефакты: таймлайн-скруббер, diff, превью UI, файлы; артефакт — первоклассный объект.
- Вмешательство одним жестом: пауза, стоп, перехват, `@исполнитель` в чате.
- Живой пульс: стрим мысли текущего исполнителя, NOX кратко комментирует.
- Уведомления только 4 типов: нужен ты, готово, провал, бюджет.
- Карточка итога: «Принять / Доработать / Откатить» (откат = git revert worktree).
- Мобильный: нижний лист «Лента · Доска · Артефакты».
- Единый поток SSE: `{agent, task, status, artifact, needs_user}`; бюджет/доверие — из Langfuse.

## 6) Метрики и путь к «80% профи»

- Главные: задач закрыто с артефактом, принято с 1-й попытки, возвраты ревизора, переделки владельцем, токены и секунды на задачу, загрузка слотов, % fast path.
- Золотой набор: 30–50 реальных задач владельца с done-if; прогон ночью после каждого изменения промптов/моделей/LoRA.
- «Профи-уровень» = задача принята владельцем без правок. Цель 80% на золотом наборе.
- Рычаги по порядку отдачи: (1) исполняемые done-if; (2) спец-модели на кодинг/UI; (3) адресный возврат ревизора; (4) best-of-N только где есть автовыбор (тесты); (5) нано-LoRA роутера/тренера на логах отказов; (6) внешний советник для сложных.

## 7) Порядок внедрения по Парето (10 шагов)

1. Сервинг: `-np 4`, слот 0 под чат, кэш префикса, `--metrics` (1 день, сразу живой чат).
2. Blackboard + SQLite-очередь + диспетчер-код + SSE-события.
3. Planner одним вызовом с JSON-схемой и done-if; fast path через классификатор.
4. Ревизор: детерминированные verify + судья по рубрике, адресный возврат.
5. Строка-статус в чате + карточка «Принять / Доработать / Откатить».
6. git worktree на исполнителя, бюджеты, чекпоинты.
7. Страж-диспетчер (systemd + lease) и арбитр GPU/обучения.
8. Тренер-правила + редкий LLM «смени подход».
9. Спец-исполнители (кодер, UI) через llama-swap; Critic и волны консилиума, внешние советники.
10. Доска/граф/таймлайн, Langfuse, золотой набор и нано-LoRA роутера/тренера.

## Где сознательно не согласился с экспертами

- **Эксперт 2 (слить всё в один Planner):** согласен частично — оставляю 2 вызова (Planner + Critic) для сложных задач, иначе теряется пожелание владельца о последовательном консилиуме волнами; для простых — 1 вызов или ноль.
- **Эксперт 2 (второй диспетчер = просто lease-строка):** дополняю — страж ещё и перезапускает зависшие задачи/сервисы, это сохраняет смысл «дублирует для контроля».
- **Эксперт 1 (10 субисполнителей = 10 очередей):** принимаю, но в UI показываю 10 исполнителей с честным статусом «ждёт слот» — владелец видит свою модель команды.
- **Эксперт 1 (spec-decoding только на чате):** принимаю; draft-модель не держу вообще из-за диска ~10 ГБ.
- **Эксперт 3 (живой пульс с фоном от нагрузки, таймлайн-скруббер):** откладываю на шаг 10 — это не создаёт артефакты, а цель владельца — закрытые задачи.
- **Эксперт 3 (граф на xyflow как основной вид):** основной вид — строка-статус и канбан; граф вторичен.
