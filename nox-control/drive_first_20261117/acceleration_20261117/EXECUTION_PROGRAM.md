## Цель ближайшего выпуска

Владелец открывает основной Резонанс, получает содержательный потоковый ответ, продолжает тот же диалог после перезагрузки. ## Программа внедрения по зависимостям

Два ближайших участка выполняются параллельно: независимое обновление Резонанса через прежний проверенный lifecycle веб-прокси и подготовка NORMAL3 через удержание старых writers/spawners. Обновление чата не ждёт optional REMOTE2 и общего перехода счётчика. Защита запуска обучения P0-A уже установлена. Native изменения остаются последовательными под существующим maintenance lease.

### P0-C. Запустить NORMAL3 в существующем NOX

Режим: три resident OS worker, а не три копии большой модели. Начальный лимит — максимум два активных CPU_LIGHT задания. READY-выбор сохраняет зависимости и приоритет P0..P3; полезность/стоимость применяется внутри разрешённого приоритета. Задачи разговора имеют приоритет.

Worker loop:
1. Сверить STOP, lease, budget и незавершённый собственный claim.
2. Взять одну готовую задачу из существующей очереди.
3. Исполнить настоящий handler, записать progress/checkpoint.
4. Сохранить result и связанную S03 receipt, затем освободить claim.
5. Взять следующую задачу без ожидания нового часа.

Отдельная совместимая правка действующего CPU-aware пула опубликована в [6f648658](https://gitlab.com/s-grouptwet/nox-helion-pp-private-build/-/commit/6f648658131bbbc6da7ecc5126b16705a4ad118c),8/8 полных readback. Она сохраняет `cpu_light_grant`, использует имеющийся STATE/S03 retirement и не подменяет модуль generic MR !205. Пропавший worker с незавершённым claim получает HOLD; после доказанного retirement новый tick получает новое fenced разрешение. Три адресные локальные проверки PASS, independent root source review PASS. Это дополнительный исходник для согласованной сборки, а не уже установленный NORMAL3.

Supervisor восстанавливает отсутствующий процесс после reconciliation его claim. UNKNOWN внешнего результата сохраняется до readback; старый action не повторяется вслепую. CPU pressure снижает допуск новых работ, но не убивает уже выполняемые полезные задачи только ради целевого числа процессов.

Приёмка:3 настоящих PID/start/heartbeat,6 уникальных существующих полезных TaskID через handler→result→S03, восстановление одного завершившегося worker без повторных эффектов. FORSAZH6 расширяет эту же схему после измерений; не является обязательной задержкой NORMAL3.

### P1. Подключить советников и прямой Drive

Советники идут через существующие native TaskID/result и реальный host-wide REMOTE2 (не локальный Semaphore). До2 общих слотов; timeout/TTL/death issuer не освобождают UNKNOWN действие автоматически. Lost ACK сверяется по исходному result. Existing CPU-only profile остаётся рабочим без зависимости от optional REMOTE2.

Источник, дата, provider и стоимость фиксируются. Используется существующая разрешённая бесплатная конфигурация; платный вызов, чужая сессия или передача управляемых connector secrets не подразумеваются.

Drive: собственный действующий OAuth/rclone NOX → небольшой upload/readback с SHA → load проверенного объекта в RAM/memfd → release по lease → actual restore. Рабочий набор ограничен физической RAM/VRAM. Drive — долговременное хранилище; удалённый файл не становится оперативной памятью от наличия ссылки.

### P1. Реальное обучение и самоулучшение

Кэш/советники уступают ресурсы обучению по checkpoint, а обучение — разговору по согласованной паузе. Проверяются реальные optimizer/scaler/RNG, продвижение шага, сохранение и восстановление. Новый checkpoint сравнивается с прежним на независимом holdout. До улучшения качества не заменяется принятый основной вес.

Увеличение контекста, KV-cache, quantization, adaptive depth и distillation включаются по одному изменению с измерением выигрыша и регрессий. Размер контекста в metadata не считается проверенной рабочей длиной. Список240 карточек продолжает эту программу: память/личность/эмоциональная модель, voice, Radio, Cinema, media и проектные навыки сохраняются; их готовность не объявляется вместе с запуском диспетчера.

## Правила ускорения и завершения

- Параллельно идут независимые участки; native запись сервера сериализуется только на время реального изменения.
- Один патч → адресная достаточная проверка → публикация → установка там, где зависимости готовы → подтверждение фактического результата.
- Optional функции не блокируют базовый чат и CPU NORMAL3.
- Исходники читаются один раз по SHA; изменённый input вызывает адресную повторную проверку.
- Неопределённый исход сначала reconcile. Законченный внешний запрос не повторяется.
- Каждая конкретная блокировка имеет input, исполнителя и следующий шаг; отсутствие input не выдаётся за отсутствие доступа вообще.
- SOURCE_TESTED, COMMITTED, INSTALLED, LOADED/SERVED и USED_WITH_DURABLE_RESULT различаются.
- Полный блок закрывается по конечным критериям выше, а не по числу отчётов, файлов или процентов без знаменателя.
