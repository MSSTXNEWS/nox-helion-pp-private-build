## Цель ближайшего выпуска

Владелец открывает основной Резонанс, получает содержательный потоковый ответ, продолжает тот же диалог после перезагрузки. Три серверных исполнителя берут настоящие READY-задачи, сохраняют результаты и восстанавливаются после сбоя. Общение получает ресурсы первым. Онлайн-советники, память, Drive-кэш и обучение подключаются по готовности своих конкретных зависимостей.

Основной Резонанс: https://clarity-sit-efficient-has.trycloudflare.com/nox-web-v29/chat.html

Веб-адрес — проверенный ранее действующий маршрут. Версия в URL не означает, что это окончательная целевая WEB-сборка. Более поздние концепции и исходники не считаются установленными по одному названию.

## Команда и непрерывная передача

Текущий сеанс: root и ровно три реальных субагента.

| Исполнитель | Владеет работой | Следующая задача после закрытия текущей |
| --- | --- | --- |
| resonance_native | Связь ответа с действительным backend, контекст, Резонанс | Подключение проверенных menu/self-model изменений и одна адресная native проверка |
| dispatcher_acceleration | Защита обучения, конечная проверка writer/spawner, NORMAL3 | Реальный ресурсный admission, непрерывная обработка очереди и восстановление |
| integrations_completion | Совместимость пакетов, советники, независимая проверка установки | Existing server-pool callbacks, REMOTE2, Drive/runtime bindings |
| root | Приоритеты, объединение, единственный согласованный native writer | Установка проверенных изменений, readback, следующий READY пакет |

После завершения отдельной задачи исполнитель передаёт TaskID, exact source/receipt, результат, ошибку при наличии и следующий шаг. Root немедленно продолжает существующего агента через followup или восстанавливает слот. Не создаются фиктивные рабочие процессы ради счётчика. Неизвестный исход внешнего действия сначала сверяется; перезапуск исполнителя не разрешает повторную отправку того же действия.

Это правило реально действует в текущей команде. Серверный автоматический respawn подтверждается только после native NORMAL3, по PID/start/heartbeat и durable TaskID/result. ChatGPT Automations и серверные workers — разные контуры. Fresh peek01:48МСК показывает15 enabled/V5; расписания в этом продолжении не менялись. Противоречащая историческая запись о rollback не заменяет это текущее наблюдение.

## Программа внедрения по зависимостям

### P0-A. Независимо поставить защиту обучения

Причина: ошибка `cgroup_headroom_gib.py` могла дать пустой CG, после чего прежняя Bash-проверка не останавливала снятие TRAIN_HOLD и запуск trainer.

Действие: установить только проверенные байты `scripts/post8098_chain_exec09.sh`. Существующий owner repair маршрут, тот же OneHost, maintenance lock, exact preimage, приватный backup, atomic replace, fsync и readback. Сервисы, counter, TRAIN_HOLD, модель и очередь этим действием не меняются.

Приёмка: exact postimage0979b337/3719B и доступный backup. Отдельно учесть, что уже работающий Bash мог прочитать старое тело; его переход будет частью согласованного lifecycle cutover. Это не запуск обучения и не proof нового optimizer progress.

### P0-B. Закончить конечную проверку старых процессов и переход счётчика

Законченные наблюдения не повторяются:
-44187317953: шесть exact launcher bodies,10523B; parent498567/start168416044 действительно `bash -s`, исторический stdin не восстановим из argv.
-44191374734: nox_kb_bootstrap.sh и cgroup_headroom_gib.py получены; прежний32KiB limit не вместил owner_qwen_execution_revision.py.
-44193822421/job134429871560: обе оставшиеся цели получены, owner_qwen_execution_revision.py45406B/SHAd3b2905c… и nox_kb_bootstrap.py13504B/SHAbc4a8849…; модель/сеть/запись/signals0,cleanupPASS.

Остаток — содержательный разбор двух новых зависимостей, точная привязка Supervisor command и lifecycle неизвестного parent/дочерних spawners. Использовать уже прочитанные тела и реальные process identities. Не разворачивать бесконечный повтор одинаковых audits.

Current counter_scope candidate должен либо замкнуть известный набор writers/spawners, либо назвать конкретный неизвестный input. Нельзя обнулить исторические4 по возрасту. Для непрозрачного Bash допускается только согласованный exact-lifetime containment с сохранением Engram holder; автоматический SIGCONT после смены generation не доказывает безопасного возврата неизвестного writer.

Cutover выполняется одним владельцем native записи: свежий owner-idle и STOP → остановка только установленных spawners → повторная проверка owner-idle перед proxy.stop → atomic common/arbiter switch → новая связанная generation → восстановление штатных сервисов. Незапущенный callback не заменяется фиктивным положительным результатом.

Приёмка: installed postimages, прежние writers действительно больше не владеют новой generation, current process binding и owner-first работают; незавершённое восстановление имеет точный статус, а не ложный полный rollback.

### P0-C. Запустить NORMAL3 в существующем NOX

Режим: три resident OS worker, а не три копии большой модели. Начальный лимит — максимум два активных CPU_LIGHT задания. READY-выбор сохраняет зависимости и приоритет P0..P3; полезность/стоимость применяется внутри разрешённого приоритета. Задачи разговора имеют приоритет.

Worker loop:
1. Сверить STOP, lease, budget и незавершённый собственный claim.
2. Взять одну готовую задачу из существующей очереди.
3. Исполнить настоящий handler, записать progress/checkpoint.
4. Сохранить result и связанную S03 receipt, затем освободить claim.
5. Взять следующую задачу без ожидания нового часа.

Supervisor восстанавливает отсутствующий процесс после reconciliation его claim. UNKNOWN внешнего результата сохраняется до readback; старый action не повторяется вслепую. CPU pressure снижает допуск новых работ, но не убивает уже выполняемые полезные задачи только ради целевого числа процессов.

Приёмка:3 настоящих PID/start/heartbeat,6 уникальных существующих полезных TaskID через handler→result→S03, восстановление одного завершившегося worker без повторных эффектов. FORSAZH6 расширяет эту же схему после измерений; не является обязательной задержкой NORMAL3.

### P0-D. Подключить умный быстрый Резонанс

- Вопросы «какая модель», «кто ты», «что умеешь» проходят действующий путь генерации с краткими проверенными фактами.
- Факты привязаны к actual selected URL данного запроса. Переход8098→8085 не переносит имя первичного backend в ответ запасного.
- Стабильный prefix сохраняется; динамические факты имеют отдельный ограниченный бюджет и не теряются при trim.
- Старый status не подменяет runtime. Проекция не публикует argv/secrets и не выдаёт имя файла за доказательство содержания весов.
- Exact menu overlay17932→9d747542 (+233B) устанавливается вместе с согласованным proxy/bridge окном.
- Первая адресная проверка после новой установки проверяет именно изменённый identity/context path и сохранение ответа. Уже завершённые проверки прежней версии не гоняются заново без причины.

Скорость проверяется сопоставимыми запросами при одинаковом лимите контекста/ответа и нагрузке. Сначала учитываются TTFT, полное время, память и качество; множитель ускорения не придумывается.

### P1. Подключить советников и прямой Drive

Советники идут через существующие native TaskID/result и реальный host-wide REMOTE2 (не локальный Semaphore). До2 общих слотов; timeout/TTL/death issuer не освобождают UNKNOWN действие автоматически. Lost ACK сверяется по исходному result. Existing CPU-only profile остаётся рабочим без зависимости от optional REMOTE2.

Источник, дата, provider и стоимость фиксируются. Используется существующая разрешённая бесплатная конфигурация; платный вызов, чужая сессия или передача управляемых connector secrets не подразумеваются.

Drive: собственный действующий OAuth/rclone NOX → небольшой upload/readback с SHA → load проверенного объекта в RAM/memfd → release по lease → actual restore. Рабочий набор ограничен физической RAM/VRAM. Drive — долговременное хранилище; удалённый файл не становится оперативной памятью от наличия ссылки.

### P1. Реальное обучение и самоулучшение

Кэш/советники уступают ресурсы обучению по checkpoint, а обучение — разговору по согласованной паузе. Проверяются реальные optimizer/scaler/RNG, продвижение шага, сохранение и восстановление. Новый checkpoint сравнивается с прежним на независимом holdout. До улучшения качества не заменяется принятый основной вес.

Увеличение контекста, KV-cache, quantization, adaptive depth и distillation включаются по одному изменению с измерением выигрыша и регрессий. Размер контекста в metadata не считается проверенной рабочей длиной. Список240 карточек продолжает эту программу: память/личность/эмоциональная модель, voice, Radio, Cinema, media и проектные навыки сохраняются; их готовность не объявляется вместе с запуском диспетчера.

## Правила ускорения и завершения

- Параллельно идут независимые участки; native запись сервера сериализуется только на время реального изменения.
- Один патч → адресная достаточная проверка → публикация → установка там, где зависимости готовы → подтверждение фактического результата.
- Optional функции не блокируют базовый чат и CPU NORMAL3.
- Исходники читаются один раз по SHA; изменённый input вызывает адресную повторную проверку.
- Неопределённый исход сначала reconcile. Законченный внешний запрос не повторяется.
- Каждая конкретная блокировка имеет input, исполнителя и следующий шаг; отсутствие input не выдаётся за отсутствие доступа вообще.
- SOURCE_TESTED, COMMITTED, INSTALLED, LOADED/SERVED и USED_WITH_DURABLE_RESULT различаются.
- Полный блок закрывается по конечным критериям выше, а не по числу отчётов, файлов или процентов без знаменателя.
