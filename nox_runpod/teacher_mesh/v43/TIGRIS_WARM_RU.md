# NOX HELION — Tigris: тёплое хранилище существующего сервера

**Статус:** исходники и автономные тесты, не подтверждена установка на GPU-сервер. НЕ создан новый сервер. НЕ удалены веса. НЕ остановлено обучение.

Облачная корзина `nox`, endpoint `https://t3.storage.dev`, region `auto`. Только S3, не S03; NOX продолжает использовать прежний OneHost и V43 Resource Brain / V95 RAM-warm.

## Как работает

- `probe` — неразрушающая проверка доступа (только list).
- `backup` — чтение *одного явно выбранного* файла весов из указанной папки и потоковая отправка в `models/sha256/<SHA256>/<имя>`. Оригинал остаётся на месте. HEAD-проверка не равна полной проверке восстановления.
- `verify` — повторно читает объект и сверяет SHA-256 всего файла (это повторный сетевой трафик).
- `restore` — сначала проверяет SHA-метаданные и свободный SSD с запасом 10 ГиБ; затем скачивает во временный файл, сверяет SHA-256 и атомарно публикует в кэш без перезаписи. Никакой автоматической очистки.

Безопасность: учётные данные только из `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` **на существующем сервере**, не в репозитории, чате или логах. Tigris выдаёт секрет один раз. Ключ должен иметь доступ только к корзине `nox`; не открывать корзину публично. Дополнительная зависимость: `boto3` в существующем Python окружении. Не ставить второй backend, supervisor, scheduler.

## Одноразовые команды на СУЩЕСТВУЮЩЕМ Vast.ai, только после защищённой установки ключей

```bash
# Секреты предварительно безопасно записаны в окружение OneHost / исполняющего пользователя.
export AWS_ENDPOINT_URL=https://t3.storage.dev
export AWS_DEFAULT_REGION=auto
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm probe

# Пример: указать реальный путь к нужному весовому файлу (не выполнять для всей папки).
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm backup \
  --model-root /root/nox --file /root/nox/models/EXISTING_MODEL.gguf

# После backup получить реальный ключ из результата, затем проверить САМ объект.
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm verify \
  --key 'models/sha256/ACTUAL_SHA256/EXISTING_MODEL.gguf'

# Загрузка назад: только если свободное место достаточное.
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm restore \
  --key 'models/sha256/ACTUAL_SHA256/EXISTING_MODEL.gguf' \
  --cache-root /root/nox/model_cache
```

Ни одна команда не перезагружает NOX, не помещает модель автоматически в VRAM, не очищает локальный весовой файл. После `restore` реальный путь передаётся существующему OneHost и штатному загрузчику, только после проверки лицензии, STOP, SHA и RAM/VRAM бюджета. V95 отдельно прогревает **уже локально имеющиеся** веса в page cache. Публичный HTTPS URL или `rclone mount` не дают произвольной модели прямой mmap-загрузки в VRAM.

### Важное ограничение диска

По состоянию последнего доступного отчёта PR #256 Vast.ai имел около 16 ГБ свободного SSD, что не подтверждено сейчас. Нельзя скачивать на него 20–70 ГБ только ради кэша. Сперва `probe`, затем `backup` выбранного существующего веса, полная `verify`, и только после отдельной подтверждённой стратегии очистки можно планировать локальный кэш. **Резервные копии S03, optimizer и checkpoint следует вести отдельно и проверять восстановлением.** Эта утилита намеренно ограничена весовыми файлами.

### Нужное для реальной активации

1. Текущий доступ к Vast #60509551 через штатный OneHost/NOX2 с подтверждённым SSH; сейчас доступа не подтверждено.
2. Секрет Tigris безопасно помещён на сервер. На скриншоте виден ID и статус Active, **но не Secret Access Key**. Нельзя восстановить секрет по ID.
3. Провести `probe`, тест `backup` небольшого несекретного весового файла, `verify` и `restore` со свободным диском, затем замер throughput и реальное использование OneHost.
