# NOX HELION — Tigris: тёплое хранилище существующего сервера

**Статус:** исходники и автономные тесты, не подтверждена установка на GPU-сервер. НЕ создан новый сервер. НЕ удалены веса. НЕ остановлено обучение.

Облачная корзина `nox`, endpoint `https://t3.storage.dev`, region `auto`. Только S3, не S03; NOX продолжает использовать прежний OneHost и V43 Resource Brain / V95 RAM-warm.

## Как работает

- `probe` — неразрушающая проверка доступа (только list).
- `backup` — чтение *одного явно выбранного* файла весов из указанной папки и потоковая отправка в `models/sha256/<SHA256>/<имя>`. Оригинал остаётся на месте. HEAD-проверка не равна полной проверке восстановления.
- `verify` — повторно читает объект и сверяет SHA-256 всего файла (это повторный сетевой трафик).
- `restore` — вспомогательный, необязательный SSD-кэш с запасом 10 ГиБ, **не основной режим**.
- `warm-ram` — основной режим NOX: по запросу читает отдельный весовой файл из Tigris **напрямую в выделенный Linux tmpfs `/dev/shm/nox_model_warm`**, проверяет SHA-256, отдаёт готовый RAM-путь существующему OneHost. Ничего не скачивает на SSD; не переключает работающую модель NOX, не меняет GPU и S03. Только если `/dev/shm`, RAM и cgroup одновременно имеют необходимый запас (по умолчанию 12 GiB). Если память не помещается — HOLD, а не принудительное вытеснение NOX.

Безопасность: учётные данные только из `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` **на существующем сервере**, не в репозитории, чате или логах. Tigris выдаёт секрет один раз. Ключ должен иметь доступ только к корзине `nox`; не открывать корзину публично. Дополнительная зависимость: `boto3` в существующем Python окружении. Не ставить второй backend, supervisor, scheduler.

## Одноразовые команды на СУЩЕСТВУЮЩЕМ Vast.ai, только после защищённой установки ключей

```bash
# Секреты предварительно безопасно записаны в окружение OneHost / исполняющего пользователя.
export AWS_ENDPOINT_URL=https://t3.storage.dev
export AWS_DEFAULT_REGION=auto
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm probe

# Пример: указать реальный путь к нужному весовому файлу (не выполнять для всей папки).
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm backup \
  --model-root /root/nox --file /root/nox/models/EXISTING_MODEL.gguf

# После backup получить реальный ключ из результата, затем проверить САМ объект.
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm verify \
  --key 'models/sha256/ACTUAL_SHA256/EXISTING_MODEL.gguf'

# Основной путь: запрос неактивного веса в RAM существующего сервера.
# Требуется заранее проверенный размер /dev/shm >= объём модели + резерв.
# Не запускает учителя автоматически и не трогает основную модель.
nice -n 10 python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm warm-ram \
  --key 'models/sha256/ACTUAL_SHA256/EXISTING_MODEL.gguf' \
  --ram-root /dev/shm/nox_model_warm --reserve-gib 12

# Необязательный SSD fallback: только если свободное место достаточное.
python3 -m nox_runpod.teacher_mesh.v43.nox.tigris_warm restore \
  --key 'models/sha256/ACTUAL_SHA256/EXISTING_MODEL.gguf' \
  --cache-root /root/nox/model_cache
```

Ни одна команда не перезагружает NOX, не помещает модель автоматически в VRAM, не очищает локальный весовой файл. После `restore` реальный путь передаётся существующему OneHost и штатному загрузчику, только после проверки лицензии, STOP, SHA и RAM/VRAM бюджета. V95 отдельно прогревает **уже локально имеющиеся** веса в page cache. Публичный HTTPS URL или `rclone mount` не дают произвольной модели прямой mmap-загрузки в VRAM.

### Важное ограничение диска

По состоянию последнего доступного отчёта PR #256 Vast.ai имел около 16 ГБ свободного SSD, что не подтверждено сейчас. Нельзя скачивать на него 20–70 ГБ только ради кэша. Сперва `probe`, затем `backup` выбранного существующего веса, полная `verify`, и только после отдельной подтверждённой стратегии очистки можно планировать локальный кэш. **Резервные копии S03, optimizer и checkpoint следует вести отдельно и проверять восстановлением.** Эта утилита намеренно ограничена весовыми файлами.

### Нужное для реальной активации

1. Текущий доступ к Vast #60509551 через штатный OneHost/NOX2 с подтверждённым SSH; сейчас доступа не подтверждено.
2. Секрет Tigris безопасно помещён на сервер. На скриншоте виден ID и статус Active, **но не Secret Access Key**. Нельзя восстановить секрет по ID.
3. Провести `probe`, тест `backup` небольшого несекретного весового файла, `verify` и `restore` со свободным диском, затем замер throughput и реальное использование OneHost.

**Нельзя считать source CI физической приёмкой работающего сервера.**


## Режим максимальной скорости NOX

- NOX PRIME закреплён за основным GPU/VRAM: не выгружаем его для учителей. Штатный диспетчер V43 должен дать разрешение на отдельный GPU/очередь и замерить RAM/VRAM до загрузки.
- Неактивные файлы весов живут в Tigris; OneHost по требованию вызывает `warm-ram` и получает SHA-проверенный путь в tmpfs. Для GGUF файл можно передать существующему штатному загрузчику. Для многокомпонентного HF safetensors все shard/tokenizer/config должны быть доступны вместе: по одному shard модель не загрузить.
- Когда модель выгружена штатным OneHost и больше не используется, освобождать её RAM tmpfs можно **только по подтверждённому owner lease**, а не автоматически удалять чужой файл.
- `/dev/shm` в некоторых контейнерах ограничен 64 MiB: если недостаточен, команда вернёт HOLD и не будет создавать новый сервер, перемонтировать tmpfs или перенастраивать GPU.
- Сеть Tigris → RAM ограничивает первый запуск; скорость последующих запросов к тому же весу определяется RAM-кэшем, пока он не освобождён.
- Нужен реальный OneHost-хук и секрет Tigris, безопасно введённый в существующий Vast #60509551: это отдельно от автономного теста и пока **не подтверждено**.


## Большие модели: native RAM / memfd (без ограничения 21 GiB /dev/shm)

По настоящему read-only preflight существующего Vast.ai #60509551 ([GitHub Actions #43648093290](https://github.com/MSSTXNEWS/nox-helion-pp-private-build/actions/runs/43648093290)) свободно **21 890 MiB** tmpfs, при **279 791 MiB** MemAvailable на хосте и cgroup headroom ≈ **66 742 MiB**. Для модели 20 GiB + резерва 12 GiB режим `warm-ram` с tmpfs здесь должен отказывать (HOLD), не переполнять память.

В том же модуле добавлен Python native-API `warm_memfd(s3, key, reserve_bytes=12*1024**3)`: S3 → anonymous Linux memfd → SHA-256 → опциональные Linux seals → объект `RAMWeightHandle`. Он **не зависит от свободного места раздела /dev/shm**, но требует свободного cgroup RAM и не вытесняет основную модель. Пример для существующего OneHost-кода:

```python
from nox_runpod.teacher_mesh.v43.nox.tigris_warm import s3_from_env, warm_memfd
# Only after OneHost owner lease / STOP / RAM+GPU budget admission.
with warm_memfd(s3_from_env(), requested_verified_key) as weight:
    # Pass weight.local to a compatible SAME-PROCESS model loader.
    # Keep handle alive until all inference consumers finish.
    native_onehost_load_from_local_path(weight.local)
    native_onehost_unload_and_confirm()
```

**Граница гарантий:** пока это только источник для нативной интеграции, не доказанное прямое монтирование веса в уже работающий движок. Пути вида /proc/self/fd/N действительны только при живом FD в том же процессе. Для многокомпонентных моделей нужен групповой manifest всех shards и tokenizer, а также проверка совместимости загрузчика. Секретный ключ Tigris на сервер не передан; фактические backup/restore и скорость S3 ещё не испытаны.
