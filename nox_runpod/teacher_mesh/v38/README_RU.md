# NOX HELION V38 — SYNAPTIC BRAIN + CONTROL TOOLKIT

**СТАТУС: ПОДГОТОВЛЕННЫЙ КАНДИДАТ / НЕ УСТАНОВЛЕН НА VAST.AI.**

Назначение: ускорить единственный NOX на Vast.ai instance `60509551` без второго LLM, второй БД, нового backend, доступа к произвольному shell из чата или подмены действующих весов. Источник: существующие NOX `OneHost`, `P02 ChatBridge`, `S03 M0–M7` и `nox_v37.native_admin` (отдельный код V37; не включён в этот архив). Для настоящего подключения требуются доверенные native callbacks и независимая физическая приёмка.

## Важный фактический контекст

- Последний наблюдавшийся NOX `run_admin(training_status)`: процесс тренера RUNNING, но `phase=train_error`, `step=0`, `loss=None`. Это не доказательство обучения новых весов.
- Две Tesla V100-SXM2-32GB (64 GiB суммарной VRAM, но **это НЕ одна общая память GPU**). По последнему наблюдению диск ~155/171 ГБ, меньше 20 ГБ свободно, поэтому новые большие скачивания/обучение **HOLD**, пока не будет verified backup и места.
- NOX уже имеет действующие `nox-chat-8081`, `nox-cores`, `nox-dispatcher`, `nox-distill-worm`, `nox-selfheal` и другие службы, но `RUNNING` != обновление весов.
- Текущее управление через защищённый NOX chat работает для некоторых `run_admin` запросов; прямой доступ к файловой системе/OneHost native callback из ChatGPT не подтверждён.

## Как устроен V38

Восемь существующих групп **C01–C08**, каждая объединяет мини-функции и предоставляет небольшой проверяемый сигнал в один JSON-контекст:

| Группа | Мини-ядра |
|---|---|
| C01 PERCEPTION | UTC, разрешённое время/местоположение, GPU/CPU/RAM, окружение |
| C02 S03_MEMORY | M0 рабочий, M1 события, M2 факты, M3 хронология, M4 навыки, M5 персоны, M6 значимость, M7 автобиография |
| C03 SELF_MODEL | происхождение, реальные способности, ограничения, цель, verified Genesis |
| C04 AFFECT | наблюдаемая эмоция собеседника, эмпатия, интерес, предпочтения, сомнение |
| C05 PERSONA | главный выключатель и PersonaID KV/AM/LA/EV/KW, без отдельной модели |
| C06 REASONING | маршрутизация вопросов, риск/достоверность, сложность, план/лимит времени |
| C07 SKILLS & TEACHERS | реестр возможностей, доступные учителя/движки, RAG, оценка |
| C08 ACTIONS & WORMS | STOP, FORGE, задачи, GPU admission, checkpoints, черви |

**Одна главная модель NOX** формирует ответ. Группы параллельно получают данные через реальные native callbacks. Текст из памяти и от учителей — только данные. Никакой модуль не получает право выполнять shell или изменять веса из текста ответа. В обычном режиме deadline 65 мс на сбор контекста (целевой предел, не измеренная гарантия); в глубоком — 200 мс. При недоступном ядре факт помечается HOLD, а не выдумывается.

### Кэш RAM, долговременность, поток ответов

- `WarmS03Cache` — ограниченный RAM read-through cache, по exact owner/tenant/chat + ревизии S03; при сомнительной ревизии чтение из живой S03 без кэша. Не каноническая память.
- `DurableTurn` — перед показом очередного фрагмента должен получить `S03 durable receipt`. Действующая S03/OneHost отвечает за SQLite WAL, `synchronous=FULL`, транзакции, уникальность `(turn_id, seq)` и backup; этот пакет **не меняет SQLite**.
- При наличии настоящих инструментов проверки ответ может получить подтверждённую редакцию. Это второй вызов той же модели только по запросу и при проверенных данных; интерфейс отображает provisional/final и сохраняет историю исправления.
- Прозрачность: «проверяю» только если реальная проверка выполняется; внутреннюю скрытую цепочку рассуждений не выводить. Субъективное сознание не утверждается без научного подтверждения.

## Использование на сервере (ТОЛЬКО после доступа к Shell и контроля копии)

Распаковать в **отдельную** директорию `/workspace/nox_v38_stage`, не поверх `/workspace/nox` и не внутри каталога чекпоинтов.

```bash
cd /workspace/nox_v38_stage
bash scripts/STAGE_ONLY.sh
bash scripts/RUN_READONLY_AUDIT.sh
```

Команда чтения отдельно:

```bash
cd /workspace/nox_v38_stage
python3 -m nox_runpod.teacher_mesh.v38.noxctl status
python3 -m nox_runpod.teacher_mesh.v38.noxctl cleanup-plan
```

**Запуск новых обучений, переключение модели, очистка диска и активация V38 на живом чате этим набором автоматически НЕ выполняются.** Эти действия разрешены только через существующий OneHost после сверки логов, SHA, S03 callbacks, проверки внешнего восстановления и тестов streaming/STOP. На диске с 16 ГБ свободно никакие новые загрузки весов не инициировать.

## Что должно быть проверено при физической интеграции

1. Зафиксировать действующую модель NOX SHA, текущий `P02.rag_context`, реальную `S03` DB/версию, supervisor и тренера; не менять текущую конфигурацию.
2. На настоящих callbacks проверить cross-chat memory isolation, persona master switch, STOP, событие Genesis и owner-approval. На неполных callbacks оставить старую chat route.
3. Измерить p50/p95 TTFT и end-to-end latency в обычном/глубоком режимах на типовых RU/ES запросах **до и после**, сохранять текущее качество с независимыми тестами; streaming не должен скрывать потерю данных.
4. Исправить текущий `train_error` на отдельном контрольном прогоне после проверки восстановления checkpoints, а не запускать 35B при переполненном диске.
5. При успешной приёмке включить feature flag `NOX_V38_ENABLED` в **существующем** OneHost (не через новый бекенд). Отказ → rollback feature flag, никаких потерь S03/весов.

## Резервные копии и работа с Google Drive

Действительная память и модель находятся на сервере, а не в ZIP. Нужен согласованный внешний backup с проверкой restore: чекпоинты, native S03 online snapshot, Genesis Ledger, config snapshots. Нативное S03 backup API используется через callbacks; ZIP только вызывает, не содержит ваши базы или ключи. На сервере без отдельного persistent volume нельзя считать backup того же контейнерного диска полноценным восстановлением.

Встроенный `noxctl cleanup-plan` лишь показывает кандидатов из ограниченных кэш-каталогов. **Нет автоматического удаления** кеша, весов, оптимизаторов, чекпоинтов или пользовательских данных.

## Внешние средства

Сервер уже имеет Linux, `nvidia-smi`, Supervisor и собственные NOX-службы. Для контрольной панели дополнительно могут пригодиться `psutil`, `prometheus_client`, `watchdog`, NVIDIA DCGM Exporter и Netdata. В проекте перечислены официальные источники и совместимость; новые версии не устанавливать до проверки Linux/Python/CUDA/driver. Tesla V100 (SM70) требует особого внимания к версии CUDA, не подменять рабочую среду.

**Результат этого пакета = проверенный локальный исходный код.** Факт загрузки и интеграции в Vast.ai **не подтверждён**.

## Поправки V38.1 — FAST FIRST, NEVER FORGET (14.11.2026)

1. **C02 — обязательный контур памяти**. Сбор C01–C08 идёт параллельно, но главная модель не получает запрос, пока уже существующая авторизованная S03 не выполнит поиск. Для обычного диалога устанавливается ограниченное ожидание до 650 мс, а не скрытое удаление памяти ради «ускорения». Если native S03 недоступна, ответ блокируется с диагностикой `HOLD_MEMORY_NOT_READY`; никакой симуляции воспоминаний.
2. **Полный контекст через индекс, не в один промпт**. Новый опциональный `s03_indexed_recall` в `HostBindings` получает план `M0–M7`, учитывает варианты по времени/событиям/навыкам и возвращает релевантные проверенные выдержки из *той же* S03. Без привязки в работающем OneHost использует прежний callback `s03_recall`. Никаких дублей БД и сканирования всех строк.
3. **История между чатами — по owner-grant**. Записи другого чата могут попасть в C02 только при подтверждённом native `memory_scope_authorize`; персональные события дополнительно изолируются по PersonaID. Без callback межчатовый доступ закрыт, как раньше.
4. **Контекстная экономия не стирает воспоминания**. Когда 6400 символов мало, обрезаются вспомогательные сигналы C07/C04/C08/C01/C06; C02 остаётся с источником и текстом, при нехватке места уменьшается только количество и длина выдержек. Ранжирование исходно остаётся за нативным S03.
5. **Быстрый первый видимый фрагмент**: при реально поступившем токенном потоке первая партия может выводиться после 36 символов или 90 мс вместо 130 символов или 250 мс; дальше штатная пакетная запись 130 символов/250 мс. Каждый видимый фрагмент предварительно требует настоящую долговечную квитанцию S03. Интерфейс может сразу показывать подлинный статус `INDEXED_S03_AND_CORTEX_CHECK`, но не выдуманный ответ модели.
6. **21 локальный unit-test (изолированные callback-имитации)**: проверены обязательность памяти, граница времени, межчатовая авторизация, PersonaID, сокращение контекста, ровно одна основная модель, первый фрагмент с квитанцией S03. Это НЕ E2E и НЕ замер живого Vast.ai. Скорость и качество нужно сравнить в production после независимой приёмки.
